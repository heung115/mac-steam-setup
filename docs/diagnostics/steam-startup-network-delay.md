# Windows Steam 시작 지연 조사 기록

마지막 갱신: 2026-08-24

## 증상

동일한 Mac, Sikarugir 래퍼, Wine prefix, Steam 빌드에서 네트워크에 따라 Windows Steam 로그인 시간이 크게 달라졌다.

| 환경 | macOS IPv4 / 게이트웨이 | 전역 IPv6 | Steam 로그인 완료 |
| --- | --- | --- | --- |
| 집 네트워크 | `192.168.0.21` / `192.168.0.1` | 없음 | 약 57초 지연 |
| 외부 네트워크 | `172.30.1.31` / `172.30.1.254` | 없음 | 반복 측정 5~6초 |

두 환경 모두 `connection_log.txt`에 IPv6 HTTP/UDP 검사 `TIMEOUT`이 기록된다. 차이는 외부 네트워크에서는 IPv6 HTTP 실패가 약 1초 만에 확정되는 반면, 집 네트워크에서는 관련 연결 검사가 약 57초 뒤에 완료된다는 점이다.

Steam 빌드는 `1785799196`이었다. 외부 네트워크 냉간 실행 기록의 예:

```text
11:57:39 Client version / connectivity test 시작
11:57:40 IPv6 HTTP TIMEOUT
11:57:44 GetCMListForConnect 시작
11:57:45 로그인 처리 완료
```

## 확인된 사실

- `-nobootstrapupdate -skipinitialbootstrap` 옵션을 유지하면 약 6초, 제거하면 약 5초였다. 이 옵션들은 57초 지연의 직접 원인이 아니다.
- 같은 Steam 설치, 로그인 캐시, `appcache`를 사용한 채 네트워크만 달라졌는데 외부 네트워크에서 반복해서 빨랐다.
- `appcache`는 조사 당시 약 82MB였다. 대형 캐시로 인한 알려진 SteamCMD 지연 사례와 양상이 다르다.
- Wine `ipconfig /all`은 기본 게이트웨이를 중복 표시했다. 집 네트워크는 94줄, 빠른 외부 네트워크도 63줄이므로 중복 표시 자체만으로 지연을 설명할 수 없다.
- macOS의 실제 외부 네트워크 IPv4 라우팅 테이블에는 기본 게이트웨이 행이 하나뿐이었다. Wine의 반복 표시는 실제 macOS 기본 경로가 수십 개라는 뜻은 아니다.
- 수동 설치 가이드도 같은 Sikarugir 엔진·템플릿 계열을 사용한다. 자동화 방식만의 구조적 차이로 지연이 생겼다는 증거는 없다.

## 효과가 없었던 실험

집 네트워크에서 다음 변경은 56~57초 지연을 없애지 못했다. 실험 후 바이너리, 레지스트리와 네트워크 설정은 원상복구했다.

- Steam `-tcp`, 비공식 `-noipv6` 실행 인자
- DNS AAAA 응답 필터링
- IPv6 검사 호스트를 `::1`로 매핑
- 로컬 HTTP 응답기로 연결 리디렉션
- macOS IPv6를 링크 로컬 전용으로 변경
- Wine `nsiproxy`에서 IPv6 주소를 숨김
- Wine의 `socket(AF_INET6)`를 즉시 실패시킴
- WinINet 자동 감지 비활성화 및 직접 연결 설정

지연 중 `Steam.exe` 다수 스레드는 이벤트/타이머 대기 상태였고 `wineserver`는 유휴 상태였다. 단순히 지속 실행되는 로컬 프록시를 추가하는 방식은 효과가 입증되지 않았고 제품 기본 동작으로 채택하지 않는다.

## 현재 판단

가장 유력한 원인은 집 공유기·회선·네트워크 필터와 Steam/Wine 연결 검사의 상호작용이다. 사용할 수 없는 연결을 외부 네트워크는 빠르게 실패시키지만 집 네트워크는 패킷을 조용히 버려 운영체제나 Steam의 약 1분 타임아웃까지 기다리게 할 가능성이 있다.

다만 집 네트워크에서 동기화된 패킷 캡처를 아직 하지 못했으므로 확정된 원인으로 표현하면 안 된다. Steam 클라이언트 버전이나 당시 네트워크 상태가 수동 설치 시점과 달랐을 가능성도 남아 있다.

## 집에서 재현될 때 다음 절차

1. 앱이나 래퍼 코드를 수정하지 않은 상태에서 집 네트워크의 IPv4와 게이트웨이가 `192.168.0.x` 계열인지 기록한다.
2. Windows Steam과 해당 래퍼의 Wine 프로세스를 완전히 종료한다.
3. 패킷 캡처와 Steam `connection_log.txt` 관찰을 같은 시각에 시작한다.
4. Windows Steam을 한 번만 냉간 실행하고 아래 시각을 기록한다.
   - Steam client 시작
   - IPv4/IPv6 연결 시도 및 응답
   - IPv6 HTTP/UDP 결과
   - `YieldingConnect`
   - 로그인 처리 완료
5. 같은 설치본을 다른 네트워크에서 다시 측정한다.

판정 기준:

- 약 57초 동안 SYN 재전송만 있고 응답이 없으면 집 네트워크 경로의 silent drop 가능성이 높다.
- 즉시 ICMP unreachable 또는 소켓 오류가 돌아왔는데 Steam만 기다리면 Steam/Wine 내부 타이머 문제에 가깝다.
- 실제 소켓 시도가 57초 뒤에야 시작하면 네트워크 I/O 이전의 Wine 어댑터·경로 열거를 더 추적한다.

## 제품 처리 원칙

- 원인이 확정되기 전에는 macOS 전체 IPv6, DNS, 기본 경로 또는 프록시를 자동 변경하지 않는다.
- `TIMEOUT` 문구만으로 장애를 판정하지 않는다. 정상적인 빠른 실행에서도 같은 문구가 기록된다.
- 제품에서 시작 시간을 관찰하고, 장시간 지연될 때 네트워크별 문제일 수 있다는 안내와 진단 로그 내보내기를 제공하는 방향이 안전하다.
- 프로세스별 즉시 거절 규칙은 패킷 캡처로 silent drop이 확인되고 실제 시작 시간이 단축되는 경우에만 검토한다.
- 외부 이슈는 사용자 승인 없이 등록하지 않는다.

## 로그 위치

설치된 래퍼 기준:

```text
~/Applications/Sikarugir/Steam.app/Contents/SharedSupport/prefix/
  drive_c/Program Files (x86)/Steam/logs/connection_log.txt
```

진단 자료를 공유할 때는 Steam 계정 ID, 로그인 토큰, 로컬 사용자 이름과 네트워크 식별 정보를 제거한다.
